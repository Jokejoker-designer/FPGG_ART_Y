# R0 accessibility — contrast measurement, 2026-08-20

Owner: `gb-accessibility`. Standard: WCAG 2.2 Level AA.
Method: `node audit/a11y/contrast-check.mjs`, which reads the real custom
properties out of `src/app/globals.css` and computes every pair the UI uses.

Every semantic role and every provenance badge colour clears 3:1 against all

`--gb-bg` text on the badge colour, and clears 4.5:1.

## Finding fixed this round

`--gb-border-strong` was `#3d4b61` and measured 2.17:1 against `--gb-bg`,
falling to 1.63:1 against `--gb-surface-3`. It marks interactive state on the
interaction rows, so SC 1.4.11 applies and it failed on every surface. Raised
to `#7c8aa0`, now 5.48:1 against the base surface.

This is exactly the class of defect a hand-computed comment hides: the previous
comment in `globals.css` asserted 14.6:1, 7.4:1 and 4.6:1 for the text tokens.
The measured values are 16.31, 8.56 and 6.10. The direction was right and the
numbers were wrong, and `--gb-border-strong` was not covered by the comment at
all. Those comments have been replaced with the measured values and a pointer
to the checker.

## Deliberate scope decisions

`--gb-border` is excluded from the 1.4.11 assertion. It is a decorative
separator: a card is already delineated by its surface change, and the border
adds no information. If it ever becomes the sole indicator of a boundary, it
must be added to `CHECKS`.

`--gb-text-faint` is asserted at the 3:1 large-text threshold rather than 4.5:1
because it is reserved for supporting labels. It happens to clear 4.5:1 as
well, but the assertion stays at 3:1 so a future palette change is judged
against the token's actual permitted use.

## Second round: axe found what the checker's role assignment missed

After Storybook was configured with `@storybook/addon-a11y` at `test: "error"`,
axe ran against all 47 stories and failed 12 of them on one rule:

```
Elements must meet minimum color contrast ratio thresholds (color-contrast)
Element has insufficient color contrast of 4.24
  (foreground #6f7c92, background #111725, 9.0pt (12px), normal)
Expected contrast ratio of 4.5:1
```

axe was right and this checker was wrong. `--gb-inactive` had been classified
as a graphical object at 3:1, but the `Pill` component renders its tone colour
as **12px text**, which is small text under SC 1.4.3 and needs 4.5:1. The same
mistake applied to every semantic role, because all of them are pill or badge
text rather than fills.

Two changes followed:

1. `CHECKS` now assigns 4.5:1 to every token used as pill or badge text. Only
   `--gb-primary-strong` (focus ring) and `--gb-border-strong` (interactive
   boundary) remain at the 3:1 graphical threshold.
2. `--gb-inactive` cannot be both visibly dim and 4.5:1 on these surfaces, so
   raising it would have collapsed it into `--gb-text-faint` and destroyed the
   hierarchy. Instead the two places that rendered it as text now use
   `--gb-text-muted` (8.56:1): the neutral `Pill` tone and the `waiting` state
   in the process strip. `--gb-inactive` is now reserved for genuinely
   graphical use and stays at 3:1, with that restriction stated in both the
   checker and `pill.tsx`.

Re-measured: 73 pairs, 0 failing. Story tests: 47 passed, 0 failed, axe clean.

The lesson worth keeping: a token's threshold follows how it is *used*, and a
checker that encodes the author's intent rather than the rendered reality will
pass while the product fails.
